## Revisions

A revision is the **game update, not the region** (RAM §0). The maintainer's Omega Ruby EUR game ("Rev 2" in the old notes) runs ORAS **v1.0** (no update). The addresses used by most community tools (PKMN-NTR, PokeReader, CitraRNG, Gen6CTRPF) are for **v1.4** (title version 7820). In the save-data heap range `0x08C6xxxx`-`0x08CFxxxx`, v1.4 = v1.0 + `0x3FF0`, proven by the CTRPF cheat DB (`[Money 999998]` `08C71DC0` vs `[Max Money, Game v1.0]` `08C6DDD0`), the Citra-Tracker v1.0 constants and the maintainer's own measurement (party `0x08CF727C`, box `0x08C9A144`). For the battle heap (`0x081Fxxxx`, `0x0820xxxx`, `0x0880xxxx`) the shift is **not** proven; the v1.0 battle addresses come from a different source (see Battle).

Old names `rev2` / `rev0_1` became `v1.0` / `v1.4` (watch keys, `MAP_ID`). Detection at runtime: the first revision (v1.0, then v1.4) whose party slot 1 decrypts with a valid checksum and species 1..721 is chosen; the watches of the other revision are released. Then a **cross-check**: the MyStatus TID must equal the OT TID of at least one party member of own origin (origin game 26/27); a mismatch logs the warning `revision cross-check failed ...` once. No verdict (and no warning) is made while no own-origin member is in the party (retried every 30th tick). The cross-check does not switch the revision; Fabio corrects addresses with the override file below.

Status letters in the table: **M** measured (first-hand or measured by tools on exactly that version), **D** derived (v1.4 community value minus `0x3FF0`, nobody measured it on v1.0), **C** community value for v1.4 (several tools agree, hardware or Citra), **U** unverified (single source, other source version or arithmetic). `-` = no address known (reported open, not guessed).

## Address overrides (no release needed)

Any address can be corrected by writing lines `key=0xADDR` into the plugin cache file `config/addresses.txt` (hex, `0x` optional, nonzero, at most 8 digits; `#` starts a comment). A line `v1.0.key=0xADDR` applies only to that revision and wins over the plain `key=` line, which applies to both revisions and wins over the built-in table. Keys: `party`, `box`, `mystatus`, `misc`, `bag`, `play_time`, `map_id`, `player_x`, `player_y`, `event_flags`, `battle_flag`, `battle_wild_foes`, `battle_trainer_foes`, `battle_wild_mons`, `battle_trainer_mons` (offsets inside a block are fixed, see the table, so correct the block start). Unknown keys, unknown revisions and unparseable values are ignored and logged as warnings. The file is read once at attach (reload the plugin). The older file `config/zone_addr.txt` (one address) is kept and equals `map_id=` for all revisions; it wins over `map_id=` in `addresses.txt`. A key without address (battle on v1.4 trainer, in-battle flag on v1.0) can be filled the same way.

## PK6 format

Source: PKHeX `PKHeX.Core/PKM/PK6.cs` and `PokeCrypto.cs` (kwsch/PKHeX); cross-check Project Pokemon save structure documentation.

- Crypto: seed = first u32 (encryption constant). `seed = seed * 0x41C64E6D + 0x6073` (32 bit), each u16 is xored with `seed >> 16`. Bytes `0x08..0xE7` are crypted; the party extension `0xE8..0x103` is crypted with a fresh stream seeded by the same constant (not a continuation of the first stream; PKHeX PokeCrypto L216-217). The 4 blocks of 56 bytes are shuffled by `(EC >> 13) & 31` taken modulo 24 (table in PKHeX `BlockPosition`). Checksum at `0x06` = u16 sum of all u16 in `0x08..0xE7`. The host helper `uz.codec.pk6_decrypt` does this; `tests/support/pk6_crypto.lua` re-implements it for tests only.
- Offsets used (decrypted): `0x00` EC u32, `0x06` checksum, `0x08` species u16, `0x0A` held item, `0x0C` TID, `0x0E` SID, `0x10` EXP u32, `0x14` ability, `0x18` PID u32, `0x1C` nature, `0x1D` bit0 fateful / bits1-2 gender / bits3-7 form, `0x1E`-`0x23` EVs, `0x40` nickname (UTF-16LE, 12 chars), `0x5A` moves 4 x u16, `0x74` IV32 (5 bits each hp/atk/def/spe/spa/spd, bit 30 egg, bit 31 nicknamed), `0xB0` OT name (UTF-16LE), `0xDF` origin game, `0xE3` language. Party extension: `0xE8` status u32, `0xEC` level u8, `0xF0` HP, `0xF2` max HP, `0xF4..0xFC` Atk, Def, Spe, SpA, SpD (PKHeX PK6.cs L375-386). Only species/EXP/checksum are verified on a device.
- Shiny: `(TID ^ SID ^ (PID >> 16) ^ (PID & 0xFFFF)) < 16`.
- Language byte (PKHeX LanguageID): 1 ja, 2 en, 3 fr, 4 it, 5 de, 7 es, 8 ko, 9 zh-Hans, 10 zh-Hant (6 is unused; it and unknown ids give `language = nil`; fixed in 0.3.3, was 6 = es).
- Origin game byte `0xDF` (PKHeX GameVersion): X 24, Y 25, AS 26, OR 27 (recalled, not re-fetched). Note: RAM §1 writes "OR=26, AS=27" for the MyStatus game byte, which contradicts PKHeX; the adapter passes the raw byte through as `trainer().version` and does not interpret it. Open.

### Live party stats (RAM §2)

Live level/HP are not in the first `0xE8` bytes. Per party slot (stride `0x1E4`) the game keeps the 22 bytes `0xE8..0xFD` of the PK6 party format at slot +0x158, encrypted with a **fresh stream seeded with the EC** (Citra-Tracker `citra-updater.py` L2427-2431 and PokeStreamer-Tools L201-204 both decrypt it this way). The adapter reads `0xE8` bytes at +0 and 22 bytes at +0x158, builds a 260-byte buffer (`0xE8` bytes + 22 bytes + 6 zero bytes) and calls `uz.codec.pk6_decrypt` (the stat stream starts at the buffer's first u32, the EC). Taken: status u32 `0xE8`, level `0xEC`, HP `0xF0`, max HP `0xF2`. Sanity check (otherwise all four stay nil and `level` falls back to the level from EXP): level 1..100, max HP 1..1500, HP <= max HP, and Atk/Def/Spe/SpA/SpD each 1..1500. The stat check goes beyond the brief: an all-zero or stale stats area decrypts to garbage that passed the level/HP checks in 20 % of 3000 random trials (measured with the synthetic crypto), the added stat check passed in none of them. The brief's old observation "level byte `0xEC` is garbage at the Rev 2 party address" is explained by reading the stats from slot +0xE8 instead of +0x158; the new layout is from the research and **not yet verified on a device**. Party count = slots with valid species.

## Level from EXP

Fallback when no live stats pass the check. Level = highest n with `exp_for_level(rate, n) <= exp`, formulas in `src/gen6/growth.lua` (Bulbapedia "Experience"). Growth rate IDs (PKHeX PersonalInfo.EXPGrowth): 0 medium fast, 1 erratic, 2 fluctuating, 3 medium slow, 4 fast, 5 slow.

## Personal table (`species_info`, growth)

`src/gen6/personal.lua`. Path `/a/1/9/5` is confirmed for ORAS (ROMFS §1, §4: pk3DS GARCReference.cs:47, GameConfig.cs:118-122); `/a/1/9/6` stays as a fallback candidate. The **last GARC file holds the whole table concatenated**, entry size `0x50` (PersonalInfoORAS.cs:7). The reader validates the last file (length divisible by `0x50`, at least 722 entries, growth byte of entries 1..721 in 0..5); per-entry file layouts (>= 722 files) are still accepted. The accepted path is logged once at info level. Entry offsets (PersonalInfoXY.cs, ROMFS §4): `0x06` Type1, `0x07` Type2 (u8, same value = single type), `0x15` EXP growth, `0x1C` u16 FormStatsIndex, `0x20` u8 FormeCount. Index of a form: species for form 0, else `FormStatsIndex + form - 1` when `0 < form < FormeCount` (PersonalTable.GetFormIndex). `species_info(species, form)` returns `{ types = { t1, t2 }, growth }`; type ids index the game text `type` list. Nothing is persisted.

## Game text (names)

`src/gen6/text.lua`. Source: ROMFS §1, §2 (pk3DS `TextFile.cs`, `GARCReference.cs`, `GameConfig.cs`, `TextReference.cs`).

- Archive: gametext GARC `/a/0/7/1 + language index` (ORAS): 0 JA kana `/a/0/7/1`, 1 JA kanji `/a/0/7/2`, 2 EN `/a/0/7/3`, 3 FR `/a/0/7/4`, 4 IT `/a/0/7/5`, 5 DE `/a/0/7/6`, 6 ES `/a/0/7/7`, 7 KO `/a/0/7/8`. The same file indices are valid in every language archive. The language comes from the MyStatus language byte (`ja` tries index 1 then 0; `zh-*` have no archive and use EN); fallback EN, then the first readable archive (an archive counts as readable with at least 115 entries and valid species and move text). All 8 language archives are present on every cartridge region (Project Pokemon file list, F).
- v0.3.1: the text file may be longer than declared (alignment padding is tolerated, a shorter file is rejected); the species file must look like the national dex list (not 100 to 721 lines, probe lines 1, 25, 150, 300, 500, 721 non-empty); otherwise the archive is searched by content, nearest file index first, for a list of at least 722 short single-word lines, and the info line at the end of loading names the file index; that line also holds the line count per kind. Name lookups accept integral floats.
- Files (GARC entry = file index + 1): species 98 (line = National Dex number), moves 14, types 18, abilities 37, natures 51, location names 90 (line = location name index, `ParentMap` of ZoneData), items 114, forms 5.
- File format (little endian): `0x00` u16 sections (1), `0x02` u16 line count, `0x04` u32 total length, `0x08` u32 initial key (0), `0x0C` u32 section data offset SDO (`0x10`); at SDO u32 section length (== total length; SDO + total == file length); line table at SDO+4, 8 bytes per line: i32 offset (relative to SDO), i16 length in UTF-16 units, 2 pad. Line i is decrypted word by word: `plain = word xor key`, `key = rotl16(key, 3)`, start key `(0x7C89 + i * 0x2983) & 0xFFFF`. Decoding: `0x0000` ends the line; `0x0010` = variable (next u16 count, next u16 code, count-1 args); code `0xBE00` becomes `\r`, `0xBE01` `\c`, `0xBE02` `[WAIT]`, `0xBDFF` (empty-line marker) nothing, any other code `[VAR xxxx]` (args skipped). Private glyphs `0xE07F` -> U+202F, `0xE08D` -> U+2026, `0xE08E` -> U+2642, `0xE08F` -> U+2640; UTF-16 surrogate pairs are combined.
- Loading: one archive read, then one file per step (8 steps), then the archive string is dropped; only the 8 parsed files are kept and lines are decoded on demand and cached in memory. Nothing is written to `uz.cache`. Names are never shipped.
- The location list of the game text has the layout of the name index of ZoneData (`ParentMap`). PKHeX's derived list shows names at even and sub-names at odd indices; we use the game text line directly and have not checked how many odd lines hold text.

## Zones and encounter areas

`src/gen6/zones.lua`. Source: ROMFS §3 (pk3DS `RSWE.cs`, `OWSE.cs`, `OWSEStructs.cs`, `mini.cs`, `GARC.cs`).

- Archive `/a/0/1/3` (encdata). Entries are classified by content: first byte `0x11` = LZ11, decompressed with `uz.codec.lz_decompress`; magic `ZO` = zone pack; magic `EN` = encounter copy pack (ORAS, ignored); no magic and size divisible by `0x38` = the zonedata table. Index positions are not relied upon (ROMFS §3 recommendation).
- Mini pack: 2-byte magic, u16 count, (count + 1) u32 offsets from the file start. ZO sub-files: [0] ZoneData (`0x38`, same layout as the table), [1] entities/scripts, [2] map script, [3] wild encounters, [4] ORAS only unknown.
- ZoneData `0x38`: u16 at `0x1C`, low 10 bits = location name index (ParentMap, gametext 90); the table record `z` belongs to zone `z`.
- Zone id: GARC index (0-based) of the ZO entry (ROMFS §3: "zone number == GARC index", index order itself is only inferred). After the scan the adapter compares the ZO sub-file 0 copies with the table records for both numberings (GARC index vs ordinal among ZO packs) and uses the one that matches better; the winner is logged (`zone ids by garc index|ordinal`).
- Encounters (ORAS): start = ZO offset[3] + `0x0E`; no table when `offset[4] - start < 0xF6` or the ZO has fewer than 4 sub-files. 61 slots x 4 bytes (`0xF4`): u16 species (bits 0-10) / form (bits 11-15), u8 min level, u8 max level; species 0 = empty. Slot order: grass 12, tall grass 12, swarm 3, surf 5, rock smash 5, old rod 3, good rod 3, super rod 3, horde A 5, horde B 5, horde C 5. The three horde groups are merged into `horde`. Slots with species above 721 are ignored. Rates (not used): grass 10x9/5/4/1 %, surf and rock smash 50/30/15/4/1, rods 60/35/5, horde A 60, B 35, C 5 %.
- `areas()`: zones with at least one valid slot, grouped by location name id, areas in order of their first zone, `zones` = zone ids with encounters, identical `{species, form, min, max}` entries removed. Route vs town has no flag; a town is simply a zone without encounters (`zone_info` still works). DexNav-only, static and gift encounters are not in this table. The kind of an encounter (grass vs surf in the live game) is **not** detectable from RAM (RAM §5, §8); consumers combine `areas()` with the manual correction.
- v0.3.1 leniency: a sub-file offset past the end or out of order only empties that sub-file (the pack stays); the encounter sub-file ends at the next larger offset (or the end of the pack) and needs at least `0xF4` bytes (pk3DS tests `0xF6` on the same tail); the zonedata table is the largest entry without magic; every non-empty table record is a zone, also when it has no ZO pack (towns), once the table matched the packs; a failing entry is skipped, not fatal; an unreadable archive is retried 20 times before `unsupported`.
- `locations()`: every location that has at least one zone, in the order of its first zone: `{ id, name, zones = all zone ids, has_encounters }`; `has_encounters` is true when one of its zones is in `areas()`. Feature flag `features.locations`. Same loading state as `areas()` (`nil, "not_ready"`).
- Diagnostics (counts only, no names): an info line when the scan ends (zone files, ZO packs, zones with encounters, areas, locations, zones from the table only, how zone ids were assigned) and a warn line when no area was found although ZO packs exist (first reason: `zo_bad_header`, `enc_too_short`, `enc_out_of_range`, `lz_failed`, `unknown_entry`, `slots_empty`).
- Scanning: 8 entries per step; the zone count of ORAS is 535 (ROMFS §3), roughly 70 steps, about 10 s at the default tick rate. Only derived numbers are kept in memory (no cache file, no names).

## Location

`location()`: zone id = u16 at `map_id` (RAM §1, hardware-confirmed on v1.4: Mauville 278, Slateport 265, Petalburg 259, Granite 78); `x`, `y` = f32 at `player_x` / `player_y`; `location` / `name` from `zone_info` once the zone scan and game text are loaded. The u16 width is as documented by the same source. `zone_addr.txt` / `addresses.txt` can correct the address. The v1.0 addresses are derived (D) and not measured.

## Trainer, badges, money, play time

`trainer()`: name, TID, SID, game byte, language from `mystatus`; money u32 from `misc + 8` (dropped when above 999,999); `badges` = popcount of the u8 at `misc + 0xC`; play time from `play_time` (dropped when minutes or seconds are 60 or more). `badges()` returns `count` and `flags[1..8]` (flag i = bit i-1). `language()` = MyStatus language byte as code; when MyStatus is unreadable the old heuristic applies (language of the largest own-origin OT group in the party).

## Poke Balls

`balls()` (since 0.6.4, contract v0.5) reads the 400 slots at `bag` and returns `{ count = n }` with n = sum of the counts of all slots whose item id is a ball. Ball ids (internal ids, no names; PKHeX Legal ball items, recalled and not re-fetched): 1..16 (Master, Ultra, Great, Poke, Safari, Net, Dive, Nest, Repeat, Timer, Luxury, Premier, Dusk, Heal, Quick, Cherish), 492..500 (Fast, Level, Lure, Heavy, Love, Friend, Moon, Sport, Park) and 576 (Dream). The list ends at the first slot with id 0. Slots with id above 775 or count 0 or above 999 are skipped; when skipped slots are at least as many as plausible ones the answer is `nil, "unsupported"` instead of a wrong number (wrong address, stale memory). `nil, "not_ready"` while no revision is found or the pouch is unreadable; `nil, "unsupported"` when the revision has no `bag` address. Caveat: a new game with a not yet filled pouch reads as 0 balls, which is also the truth. Nothing here was checked on a real game: Fabio should compare `balls()` with the in-game bag on v1.0 (and v1.4) and correct `bag` through `config/addresses.txt` if needed.

## Bag (0.7.0)

`bag()` and `encode_item(pouch, item, count[, slot])` (contract v0.6) work on the five pouches behind the `bag` address. Each slot is 4 bytes, u16 item id + u16 count, little endian, packed from slot 0 (an id of 0 ends the list):

| Pouch | Offset from `bag` | Slots | Max count |
|---|---|---|---|
| `items` | `0x000` | 400 | 999 |
| `key_items` | `0x640` | 96 | 1 |
| `tms` | `0x7C0` | 108 | 1 |
| `medicine` | `0x970` | 64 | 999 |
| `berries` | `0xA70` | 72 | 999 |

Sources: Citra-Tracker-v2 `util/bagfuncs.py` ORAS list `[147250640, 9952, 10208, 10640, 11024, 12624]` (distances below the money address give 0x000 / 0x640 / 0x7C0 / 0x970 / 0xA70 relative to the Items pouch, which matches the PKHeX SAV6AO `MyItem` pouch offsets as recalled, not re-fetched); slot counts are the distances between the offsets divided by 4 (the Berry pouch size 72 follows PKHeX InventoryPouch6, recalled). Count limits: PKHeX max count 999 for ordinary pouches; 1 for key items and TMs/HMs is an assumption. Item id limit 775 as for `balls()`.

`encode_item` reads the pouch, edits the packed list and returns the write ops for the changed slots only (removal compacts the list, the vacated slot is zeroed). A pouch with mostly implausible slots (id above 775 or count 0 or above the pouch limit) is treated as garbage and answers `unsupported`. Not yet checked on a real game. Open: whether the TM/HM pouch is a packed list or fixed slots in the real game (treated as packed), and the item-to-pouch assignment (not validated; the Creature Editor must pick the pouch).

## Battle and encounters

`src/gen6/oras_battle.lua`. Sources: RAM §5, §6; Gen6CTRPF Codes.cpp L5728-5741 ("struct fills a frame or two after the in-battle flag rises"; wild PK6 has an empty OT name); Citra-Tracker (v1.0 wild/trainer detection: opponent buffer slot 0 decrypts to species 1..807 and the pp byte is below 65).

The opponent party buffers and the battle-mon arrays **persist after a battle**, so "in battle" is inferred:

- **Start**: slot 1 of an opponent buffer (`battle_wild_foes` or `battle_trainer_foes`; the raw first `0xE8` bytes are compared every tick, the first reading is the baseline) changes and decrypts to a valid checksummed PK6 (species 1..721), and within 150 polls the battle-mon array of that kind holds a plausible entry (species 1..721, max HP >= 1, HP <= max HP, level 1..100) matching the foe by species and level, and where the in-battle flag is known (v1.4) it reads `0x00040001`. Without a battle-mon array address (v1.4 today) the flag alone confirms. Wild vs trainer = which buffer changed.
- **Foes**: the valid buffer slots that match an unused battle-mon entry (scanned from the end of the array; own mons come first); HP, max HP and level come from the battle-mon entry. Without an array the wild slot 1 and, for a horde, slots 2..5 are used. **Horde** = foe slots 2..5 all valid (and matched). Stale slots of an older battle in the same buffer are ignored when an array exists.
- **Own** (`battle().own`): the remaining battle-mon entries matched to party members by species and level; `personality` and `slot` from the live party, `hp`/`max_hp` from the battle-mon entry, so a faint in battle (HP 0) is visible while the party stats are still stale.
- **End**: the in-battle flag drops, or the zone (`map_id`) changes, or the overworld position changes by more than 0.01, or no battle-mon entry matches any foe for 3 polls in a row (array cleared). A battle that ends without the player moving (flee, catch, faint) is therefore detected late, when the array is cleared or the player moves.
- **Encounters**: each wild battle start appends `{ seq, species, form, level, shiny, horde, zone, location, frame }` (frame from `uz.memory.frame()`), last 64 kept; trainer battles add none.
- Events: `battle.started`, `encounter` (wild only), `battle.ended`.

**Unverified for the real game (Fabio must check):** all v1.0 battle addresses (`battle_wild_foes`, `battle_trainer_foes`, `battle_wild_mons`, `battle_trainer_mons`; arithmetic of the Citra-Tracker constants), the battle-mon field offsets on v1.0, that the opponent buffer slot layout has the party stats at +0x158 (assumed from `party`), whether the buffers really change at battle start and stay valid, the stride/count of the battle-mon array in doubles and hordes (8 entries read), and the end conditions. There is no v1.0 in-battle flag. The v1.4 trainer buffer and battle-mon arrays are open. Any of them can be replaced through `config/addresses.txt`.

## Icons

`src/gen6/icons.lua`. `icon(species, form)` returns the PNG of the box icon (`uz.codec.bclim` + `uz.codec.png`). The research lists `/a/0/9/1` ("971 box sprites", F) but the discovery stays content based. Assumptions to verify locally:

- Discovery: `uz.rom.romfs_list` walked recursively from `/a`, one directory or one candidate per step. Candidates are files of 256 KiB to 16 MiB. A candidate is accepted when `uz.codec.garc` reports 700 to 1100 entries and the entries of species 1, 25, 150, 300, 500, 700 (GARC entry species + 1, sub-file 1) decode as BCLIM with a size in {40x30, 32x32, 64x32}. A path can be forced by writing it into the cache file `config/icon_garc.txt` (it is still validated).
- Mapping (measured 2026-10-26 on a real Omega Ruby EU, all 974 entries compared by eye): the icon GARC is **not** indexed by species or by personal form index. Entry 0 is a placeholder, entries 1..972 hold all species in groups (dex order for 1..649, Gen 6 species 650..721 in an internal order), each group holding the species' megas, forms, gender or variant icons, entry 973 is the egg. `src/gen6/icon_order.lua` stores the measured numbers (own table keyed by species ID: first entry, group size, position of form 0, known positions of forms 1..k; no names). `entry(species, form)` returns first + position; an unknown form position returns the base icon with `exact = false` (not cached under the form key). `icons.lua` uses the table when the accepted GARC has exactly 974 entries, otherwise it keeps the old guess (species, or the personal form index). Positions of some forms are still unknown and show the base icon.
- Entries: every GARC entry is read through `gen6.garc_entry`, which LZ11-decompresses entries whose first byte is 0x11 (pk3DS GARCEntry; output limit 4 MiB, raw entry kept on failure). Open: whether the icons use the Gen 6 palette BCLIM variant (format 7 with pixel data starting `02 00`, pk3DS BCLIM.cs); the player's decoder does not handle it yet.
- Diagnostics (0.3.3): `icons_state`, `icons_path` (accepted archive, else the probe path `/a/0/9/1`), `icons_count` (GARC entries, -1 unreadable), `icons_garc_ok` (1/0), `icons_garc_error`, `icons_first_rejection`, and per probed entry (0-based entries 1, 25, 700, prefix `icon_e1`, `icon_e25`, `icon_e700`) `_first` (first byte, hex), `_lz11` (0/1), `_lz_failed`, `_size`, `_fmt` (BCLIM format byte, -1 without footer), `_w`, `_h`, `_px0` (first u16 of the pixel data, hex). No pixels, no names.
- Cache (before 0.3.4): `icons/<species>-<form>.png`. `features.icons` becomes true when the archive is found; discovery starts after 90 ticks.
- Decoding (0.3.4, `src/gen6/pal_bclim.lua`): field report 2026-10-18 on a real game: 974 entries at `/a/0/9/1`, entries 1/25/700 LZ11, decoded 4136 bytes (4096 data + 40 footer), BCLIM format 7, 40x30, first u16 of the data `0x0002`. The app's `uz.codec.bclim` takes every format 7 image starting with u16 2 for the Gen 6 palette variant (u16 2, u16 count, palette, indices) and showed dark glyph-like shapes. **Finding:** 4096 is exactly 64 x 32 x 2, the size of a plain tiled 16-bit texture (RGBA5551, stored 64x32, cropped to 40x30); a first pixel of 0x0002 is a transparent pixel (A bit 0). Layout rule in `pal_bclim.layout`: data size = pow2(w) x pow2(h) x 2 means `plain16` (decoded in Lua as RGBA5551 Morton 8x8 tiles), else the palette signature means `palette`. Both decoders are Lua; `icon()` uses `uz.codec.bclim` only for other BCLIMs. **Unconfirmed:** that the real icons are plain16 (the new `icon_e1_layout`, `icon_e1_head`, and for palette data `icon_e1_count/pal/idx/idxbytes` diagnostics show it) and, for palette data, which of the four readings is right.
- Palette variants (pk3DS `BCLIM.cs`: the reader takes RGB565 colours, low nibble first, BaseSize^2 indices with BaseSize = next power of two of max(w, h); the writer takes RGBA5551, transparent pixels forced to index 0, first pixel in the HIGH nibble): `icon_variants()` returns A RGB565 + index 0 transparent + low nibble first, B RGBA5551 + low nibble first, C RGB565 + index 0 transparent + high nibble first, D RGBA5551 + high nibble first, and E plain tiled RGBA5551 (plain16 data only). `icons.lua` decodes with `pal_bclim.DEFAULT_VARIANT` for palette data and as plain texture for plain16 data. **Confirmed on a real Omega Ruby EU (second field report): the icons are palette images (u16 2, 12 colours, 4-bit indices of the 64x32 tiled image, zero padding up to 4096 data bytes) and only variant D (RGBA5551, index 0 not forced transparent, first pixel in the HIGH nibble) gives clean, correctly coloured icons; `DEFAULT_VARIANT` is `"D"`.** `layout()` therefore returns `palette` instead of `plain16` when the size matches a plain texture but the palette signature holds (u16 2, count 1..256), the palette plus the index bytes needed for the image fit and everything after them is zero; a plain texture has nonzero trailing data and stays `plain16`. `icon_variants()` lists the default variant first. Icons with more than 16 colours use 8-bit indices (1 byte per pixel, same 8x8 Morton tiling, 8 tiles per row, crop 40x30), zero-padded to 4096 data bytes; `layout()` returns `palette` for them too and `decode` reads 8 bit (synthetic test with 20 colours).
- Debug export (0.4.1): once per game session, as soon as icon discovery has accepted the archive, the adapter writes the DECOMPRESSED bytes (exactly what the decoder gets) of the 0-based GARC entries 0, 1, 25, 201, 255, 258, 261 and of the current team species (entry = species; only if the team is known at that moment; at most 12 `.bin` files) to the plugin cache as `diag/icon-<entry0>.bin`, plus the undecompressed bytes of entries 1 and 255 as `diag/icon-<entry0>-raw.bin`. `diag/icon-index.txt` has a header line (GARC path, entry count, GARC version and data offset as far as the codec reports them, FATB sub-file counts of the first 8 entries, `n/a` when unavailable) and one line per entry (`<entry> comp=<bytes> decomp=<bytes> head=<first 16 bytes hex> footer=w=<w> h=<h> fmt=<fmt>`). The work is time-budgeted (25 ms per tick) and never throws. Diagnostics key `icon_export` is `pending`, `done:<n> files` (n counts the `.bin` files plus the index) or the failure reason (`no_icon_archive`, `garc_unreadable`, `write_failed`, `unsupported`). The files stay in the cache on the player's PC; they are never logged and must never be committed to the repository (Fabio sends them privately for analysis only).
- Cache (0.3.4): `icons/<species>-<form>-<rev>.png` with `rev` = `icons.CACHE_REV` (`r3-o1`: r3 = variant D palette decoder, o1 = measured icon order; PNGs of earlier revisions are ignored). The same string is `info().icon_rev` so consumers can key their own caches, index `icons/index.txt`.

## Region map

`src/gen6/maps.lua`, `src/gen6/darc.lua`. The real map image is read from the user's game, none is drawn. Region map image: **not found** in the research (ROMFS §7); candidates from the Project Pokemon list (F): `a/0/6/7`, `a/0/6/8` (town map UI), `a/2/4/8` (PokeNav location screens, `a/2/4/7` header), `a/2/7/6` (map navi buttons).

- Scan: those four archives are read **first**, then every other RomFS file from `/a` in path order (files larger than 32 MiB or smaller than 64 bytes are skipped). One file is read per step. In each file: if `uz.codec.garc` parses it, every entry (sub-file 1, at most 5000 per file, 16 per step) is examined, otherwise the file itself is entry 1. An entry is checked as plain BCLIM (footer `CLIM` + `imag`), as LZ10/LZ11 data (first byte 0x10/0x11, compressed size up to 2 MiB, decompressed up to 4 MiB, then re-checked once) and as DARC (magic `darc`, files checked as BCLIM regardless of name).
- Threshold: size at least 256 px wide and 128 px high (from the `imag` header). Every candidate is decoded once with `uz.codec.bclim` and **dropped when mostly noise**: of up to 64 x 128 sampled horizontal neighbour pixel pairs (pairs with both pixels fully transparent skipped, at least 200 pairs needed) more than 50 % differ by more than 96 (sum of the RGB differences, maximum 765). A garbage decode of a wrong candidate differs at nearly every pixel; real maps and UI textures have large smooth areas. A candidate that cannot be decoded is kept. Up to 2000 candidates are stored, `map_candidates()` returns the 40 largest by area. The thresholds (96, 50 %) are guesses to tune against the real game.
- id = `<romfs path>#<garc entry, 1-based>[/<darc file path>]`, a loose BCLIM file uses entry 1.
- DARC layout (3dbrew, recalled, unverified on real files): header `darc`, BOM, header size, version, file size, table offset, table length, data offset; 12-byte table entries (name offset with flag byte 1 = directory; directories hold parent and end index, files hold data offset and length); names UTF-16LE behind the table. Only ASCII names are kept; directory depth up to 16.
- Cache: `map/index.txt` (`complete`/`partial` + `id`, width, height), `map/files.txt`, `map/progress.txt` (files finished; saved every 10 files, resumable), PNGs `map/<hash>.png`. A PNG above 1 MiB gives `nil, "too_large"`. `features.map` is true when the scan finished with at least one candidate; the scan starts after 120 ticks. Caches written by v0.2 (sorted file order, no noise filter) keep their index; delete `map/` in the plugin cache to rescan.
- Scan (0.3.4): `maps.STEP_BUDGET_MS` (25 ms of `uz.clock`) per `step()`, called from `tick()` on ticks % 4 == 3 (about 7 times per second at 30 Hz) and by every `map_candidates()` poll. Before 0.3.4 one step was one unit (a directory, an archive open or 16 entries) every 8 ticks (about 4 units per second) and all entries of all archives were read and, if they started with 0x10/0x11, decompressed; with hundreds of archives and a 974-entry archive alone needing 61 units that is far beyond 5 minutes (the exact RomFS entry count was not measured). Now an entry is skipped without decompression when its LZ header announces fewer than `MIN_DECODED` (16424) bytes (a 256x128 4-bit texture plus footer) or its GARC length is below 40 bytes. A throwing entry, archive open or listing is counted (`map_errors`), recorded (`map_first_rejection`) and skipped, never retried. The scan ends in `done` (list, possibly empty) or `failed` with `map_fail_reason` (`time_limit` after 30 minutes of `uz.clock`, `too_many_errors` after 500 errors); `failed` keeps the partial list (`map_candidates()` returns it, or `nil, "unsupported"` when empty). Priority archives first, then every other reachable archive in path order. Cache key `maps.CACHE_REV` = index format `3` + scan revision `MAP_SCAN_REV` (`m2`) + plugin version, e.g. `complete 3-m2-0.6.3` (0.6.3; before it was only `complete 3`, which let a result of an older core survive an update). The index header and the name of every cached PNG carry it, so any other header, also `complete 3`, is ignored and the scan starts again from the directory walk; bump `MAP_SCAN_REV` whenever the scan rules change. LZ input and output limits are 8 MiB (a 1024x1024 RGBA8 texture is 4 MiB plus footer, the largest the GPU takes).
- Region map location: still **unknown** (no public source; RomFS research section 7). Only the Project Pokemon list names `a/0/6/7`, `a/0/6/8`, `a/2/4/8`, `a/2/7/6` (F). Large textures may also be BCH, split into tiles or in a mini pack; the scan only recognises BCLIM (plain, LZ-wrapped, in DARC) and does not read GARC sub-files after the first. Open.
- `map_selected()` reads `MAP_ID` in `maps.lua` (empty: "fill after Fabio confirms"), keyed by game id, optionally a table per revision name (`v1.0` / `v1.4`).
- The size threshold has always been a minimum (256 x 128), larger textures are accepted and ranked first by area; the field report on 0.6.2 (40 listed candidates, all 320x240 / 400x240, no Hoenn map) came from a stale index. Whether a rescan finds the map is unverified. Open: whether the region map is a BCLIM at all, its real size, and whether it is LZ-wrapped or in a DARC. Several candidates will show up; the maintainer chooses with `map_candidates()`/`map_image()`.

## Writing (0.5.0)

`encode_pokemon` rebuilds a party or box structure; it reads the current bytes (party slot `+0x00`, 0xE8 bytes, plus the 22 live stat bytes at `+0x158` when they pass the live sanity check), decrypts them (`gen6.pk6.decrypt`), edits the fields, recomputes the checksum at `0x06` (u16 sum of `0x08..0xE7`), and encrypts with the unchanged encryption constant (`gen6.pk6.encrypt`). Offsets beyond the read list above: PP `0x62` (4 x u8), PP ups `0x66` (4 x u8), nickname `0x40` (13 UTF-16LE units), the party extension `0xEC` level / `0xF0` HP / `0xF2` max HP / `0xF4..` stats (PKHeX PK6.cs, recalled, not re-fetched). Limits (PKHeX Legal.cs): species 721, move 617, item 775, ability 191. Stats: `HP = (2B + IV + EV/4) * L / 100 + L + 10`, others `((2B + IV + EV/4) * L / 100 + 5) * nature`, base stats are bytes `0x00..0x05` of the personal entry (HP, Atk, Def, Spe, SpA, SpD; PKHeX PersonalInfo, not verified on a device). Shiny: Gen 6 rule `TID ^ SID ^ PID_hi ^ PID_lo < 16`; only `PID_hi` is changed. `encode_money` writes the u32 at `misc + 8`. Unknown and therefore unsupported: bag pockets and item slot offsets (`encode_item`), move PP table (new moves need an explicit `pp`), ability slot/hidden ability flag handling on a species change. Nothing of this was tested on a real game.
